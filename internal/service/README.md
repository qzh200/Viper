# internal/service

**顶替模式**的协议实现：让官方 PredatorSense 应用改连 Viper。

官方应用**按端口号**连接本机的一个服务来读写机器状态，谁占着这个端口，
它就跟谁说话。Viper 提供同一个服务，官方应用就会改连 Viper。

```
请求： "ACER" + uint32(小端) 包标识 + JSON 负载
应答： 纯 JSON 文档（jsoncpp StyledWriter：Tab 缩进、成员按字节序排序、
       浮点 %.17g 并补 .0、成员值是对象或数组时冒号后换行）
包标识： 0 初始化 / 10 监视数据 / 20 读设置 / 30 设备 / 40 灯效能力 / 100 写设置
```

## 它和客户端路线的关系

这一层是**顶替模式**。硬件层的客户端路线（见 `internal/machine`）靠原厂
程序问机器；顶替模式是原厂服务被停掉、Viper 自己顶上它的端口。

两个模式**互斥**，手动切换：

| 模式 | 原厂服务 | 谁占着 46933 | 数据源 | 管理员权限 |
| :--- | :--- | :--- | :--- | :--- |
| 客户端模式（命令行） | 在跑 | 原厂服务 | 原厂服务 | 不需要 |
| 顶替模式（`viper-service`） | 停掉 | Viper | 固件那一侧 | 需要 |

顶替模式的前提就是原厂服务已经停掉——客户端那条路这时不可用，所以它的
数据源是固件那一侧（`internal/hardware`）。

## 应答的形状

| 情形 | 应答 |
| :--- | :--- |
| 答得出来 | `{"data":…,"request":"<函数名>","result":"0"}` |
| 写设置成功 | `{"request":"<函数名>","result":"0"}`（**没有 data 字段**） |
| 写设置失败 | `{"request":"<函数名>","result":"4"}` |
| 固件不支持的能力 | `{"request":"<函数名>","result":"3"}`（**没有 data 字段**） |
| 不认识的请求 | `{"data":null,"request":null,"result":"0"}`（空应答） |

最后两种没有 data 字段的应答是照着原厂服务抓包来的：

* `SUPPORT_OVERCLOCKING_MODE_CAPABILITY` → `{"request":"SUPPORT_OVERCLOCKING_MODE_CAPABILITY","result":"3"}`，
  原厂服务自己也不实现这个能力。
* 包标识 40（灯效能力）→ `{"data":null,"request":null,"result":"0"}`，原厂服务
  不实现这个请求，只给一个空应答。`Provider.LightingEffects()` 仍然留着，
  它只是给本程序自己用的简表，不进协议。

## 服务自己记住的设置

有三项设置**固件里没有它们的影子**，服务读不到，也没法从机器上问出来：

| 设置 | 固件里的来源 | 服务的做法 |
| :--- | :--- | :--- |
| `BATTERY_BOOST` | 无 | 服务记住自己写过的值，没写过就报原厂的值 `1` |
| `SOUND_MODE` | 无（声音芯片不归游戏硬件提供者管） | 服务记住自己写过的值，没写过就报 `{"function":"DTS","mode":0}` |
| `CUSTOM_BOOT_LOGO` | 无（本机固件不支持启动标志） | 服务记住自己写过的值，没写过就报 `{"imageSource":""}` |

**这三个值是服务自己的记录，不是从固件读回来的值。** 它们只活在服务进程的
内存里，服务一重启就回到原厂的默认值。实现见 `remembered.go`。

## 没有管理员权限的时候

游戏硬件提供者需要管理员权限。拿不到的时候服务照样跑，只是答不出那些需要
机器的设置（读的时候答 `result":"3"`，写的时候答 `result":"4"`）。

**这里有个 Go 的陷阱**：把一个空的 `*hardware.Backend` 放进接口字段，接口
跟 `nil` 并不相等，`p.backend == nil` 恒为假，二十来处守卫会全部失效，
第一个需要机器的请求就会把服务进程打崩。修法有两层：

* `cmd/viper-service/main.go` 用接口类型 `hardware.Gaming` 声明提供者，
  失败时放进去的就是真 `nil`；
* `internal/service` 的 `NewProvider` 与 `hasBackend()` 都会去看指针本身
  （`reflect`），绕过了构造函数也认得出来。

回归用例在 `typednil_test.go`。

## 灯效的钳制

服务层与 `internal/app` 层用同一套范围（来自原厂档案）：速度 `1`–`9`、
方向 `0`–`1`、亮度 `0`–`100`。写进机器的值与存下来的值都先被拉进范围，
两层对同一个数字的理解必须一样，否则官方应用看到的值与 Viper 存下的值
就会对不上。

## 测试

```powershell
go test ./internal/service/...
```

用例锁的是实测结论：应答的字节形状、初始化能力表、灯效的九种模式、
钳制范围、以及没有管理员权限时的行为。

`cmd/padiff` 会把本服务与原厂服务的应答逐项对照（28 个请求），结果是 25 个
结构完全一致、2 个字节级完全一致，剩下三个的差异都有可解释的原因。
